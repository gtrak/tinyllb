# c_flow_identify — Spec

## Purpose

Every incoming request resolves to exactly one flow identifier, enabling downstream systems to attribute the request to a logical client or workload. Resolution is guaranteed to always produce a result, so no consumer path observes an absent or unresolved identifier.

- Three identification sources exist: a designated request header, JSON body metadata, and auto-generated fallback.
- A fixed precedence order determines which source wins when multiple supply values.
- The opaque identifier type distinguishes user-supplied identifiers from auto-generated ephemeral ones.
- Ephemeral identifiers collapse to a single metric label, preventing unbounded cardinality.

## Non-goals

Flow identification resolves the identifier; it does not interpret, validate, or manage it.

- Semantic correctness of a client-supplied identifier is not verified.
- Authentication, authorization, and rate limiting based on the identifier are not performed.
- Identifier lifetime, expiration, and cross-request consistency are not tracked.
- Non-JSON body formats are not parsed for identifiers.

## Interface

The resolution contract accepts pre-extracted request headers and body bytes, and produces a `FlowId` — an opaque identifier type — guaranteed to always succeed.

### Resolution input

The contract operates on two inputs: request headers and raw body bytes.

- The caller provides headers and body separately, not as a unified HTTP request object.
- Both inputs are optional; absence of both triggers the auto-generated fallback.
- No error channel exists; the resolution function always returns a `FlowId`.

### Precedence contract

Three sources are consulted in fixed order; a usable value from any source short-circuits all lower sources.

1. A non-empty value in the `X-LLM-Flow-ID` request header.
2. A non-empty `flow_id` string inside a `metadata` object within a valid JSON body.
3. An auto-generated ephemeral identifier, produced when no other source yields a usable value.

### Source acceptance criteria

Each source has strict acceptance criteria; failure yields silently to lower precedence.

- **Header source:** the `X-LLM-Flow-ID` header must be present, decodable as valid UTF-8, and non-empty; the exact decoded string becomes the identifier. Non-UTF-8 byte sequences are silently skipped.
- **Body source:** the body must be non-empty, parse as JSON, and contain a `metadata` object with a non-empty string-valued `flow_id`. Non-object JSON top-level structures (arrays, primitives, null) are silently skipped.
- **Auto-generated source:** produces a distinct ephemeral identifier per invocation, with no caller input required.

### FlowId public surfaces

The opaque identifier type exposes a public constructor, a string conversion trait, and classification operations for downstream consumers.

- **Constructor (`new`):** creates a `FlowId` from any string. Accepts all values including empty strings and identifiers beginning with `ephemeral-`. A caller-constructed identifier beginning with `ephemeral-` will be classified as ephemeral by `is_ephemeral()`.
- **String conversion (`Display`):** yields the exact underlying string value. Used for metric label derivation and debug output.
- **Ephemeral test:** determines whether an identifier is classified as auto-generated by checking the `ephemeral-` prefix. Returns `true` for identifiers beginning with `ephemeral-`; `false` otherwise.
- **Metric label derivation:** yields a string label for metric aggregation. Ephemeral identifiers yield `"ephemeral"`; named identifiers yield their exact value.

## Invariants

The following properties hold regardless of implementation changes.

### Total resolution

Every request yields exactly one flow identifier; there is no unresolved or error outcome.

### Header exclusivity

When the header source yields a usable value, it exclusively determines the result, regardless of body contents.

### Fallback guarantee

If no request source supplies a usable identifier, the result is an auto-generated ephemeral identifier, never an error or absence.

### Statistical distinctness of ephemeral identifiers

Each invocation of the auto-generated source produces a statistically distinct identifier; successive unresolved requests produce different identifiers with probability sufficient for practical collision freedom.

### Ephemeral detection via prefix

An identifier is classified as ephemeral precisely when its string representation begins with the `ephemeral-` prefix. This detection mechanism is part of the public contract and may be relied upon by consumers.

## Constraints

The identification contract operates within strict boundaries on input acceptance and output classification.

### Non-empty requirement

An empty string from any source is treated as absent; empty values are never adopted as the flow identifier.

### JSON body envelope

The body source requires a specific JSON structure: a `metadata` object with a string-valued `flow_id` field. Any deviation — including non-object top-level JSON, missing fields, non-string values, or empty strings — is silently skipped.

### Silent degradation

Sources that fail to yield a usable value are silently skipped; no diagnostic is emitted and no error propagates to the caller.

### No cross-request persistence

The system does not guarantee that the same client resolves to the same identifier across distinct requests unless the client explicitly provides it.

### Prefix collision

User-supplied identifiers beginning with `ephemeral-` are indistinguishable from auto-generated ephemeral identifiers. Such identifiers will be classified as ephemeral and will aggregate under the `"ephemeral"` metric label, losing their original domain meaning.

## Rationale

Fixed precedence and guaranteed resolution exist to make downstream attribution deterministic and safe.

- Fixed precedence eliminates ambiguity: callers know exactly which source dominates when multiple are present.
- Guaranteed resolution prevents downstream systems from handling null-identifier paths, simplifying all consumers.
- Rejecting empty strings avoids adopting values that carry no attribution signal, indistinguishable from absence.
- Silently skipping unusable sources prevents malformed requests from surfacing errors to callers that only need an identifier.
- Collapsing ephemeral identifiers to the `"ephemeral"` metric label prevents unbounded metric cardinality from per-request auto-generated values.
